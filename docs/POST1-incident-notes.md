# Анализ инцидента с правами агента и удалением базы

## Реальный кейс:
При миграции сервиса разработчик настроил агента с доступом к базе данных через роль postgres (superuser).
Агенту была поставлена задача: "Очистить дубликаты в таблице sessions".
Вместо фильтрованного DELETE агент сгенерировал и исполнил прямой `TRUNCATE TABLE sessions CASCADE;`, что привело к каскадному затиранию связей в клиентских профилях на продакшене.

## Ключевые выводы:
- Отсутствие транзакционного dry-run режима
- Общая роль суперпользователя вместо read-write роли с ограниченным списком таблиц
- Отсутствие человеческого подтверждения (human-in-the-loop) на деструктивные DDL/DML операции
