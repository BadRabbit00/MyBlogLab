# Проверка ответов модели

`src/validation.py` задаёт общий контракт: тело поста должно быть обычным текстом.
`validate_plain_text(text)` возвращает причины отказа, а `require_plain_text(text)`
выбрасывает `ResponseValidationError` с теми же причинами в поле `errors`.
Дополнительные библиотеки не нужны.

## Что отклоняется

- Китайские иероглифы, радикалы и совместимые формы Han, включая дополнительные
  плоскости Unicode. Диапазоны взяты из
  [Unicode 17.0 Scripts.txt](https://www.unicode.org/Public/17.0.0/ucd/Scripts.txt).
  Общие с японским и корейским иероглифы тоже отклоняются.
- Markdown: выделение, обратные кавычки, блоки кода, заголовки, списки, цитаты,
  разделители, таблицы, оформленные ссылки, изображения, сноски и явные переносы строк.
- HTML/XML: теги, комментарии, декларации, CDATA и закодированные HTML-сущности.
- Шаблонные разделители Jinja/Twig/Mustache/ERB, BBCode, распространённая разметка
  LaTeX, JSON-обёртки, YAML-поля ответа вроде `text:`/`content:` и оставшиеся служебные
  токены модели.
- Пустые ответы, значения другого типа и скрытые управляющие символы.

Проверка рассматривает также NFKC-представление Unicode, чтобы полноширинные
скобки и другие совместимые варианты не обходили правила. Сам текст не изменяется.
Это проверка символов и синтаксических признаков; она не определяет язык каждого
слова и не проверяет достоверность технических утверждений.

Обычная пунктуация, абзацы, латинские названия, `snake_case`, флаги `--help`,
сравнения `x < y`, неоформленные URL, эмодзи и каомодзи допустимы. Двойной дефис
как самостоятельный разделитель отклоняется. Текст технического примера с разметкой
тоже отклоняется: в готовом посте команды нужно писать без оформления.

## Где действует проверка

1. `src.llm.generate` отделяет ведущий канал размышлений и конечные токены Gemma,
   затем проверяет ответ. Разметку из ответа не вырезает. Отклонённые ответы и причины
   записываются в `logs/{post_id}.jsonl`. Следующая попытка получает причины отказа.
   Число запросов ограничено `max_retries` (по умолчанию 3).
2. `lint_post` применяет эти же правила на стадиях draft, critique и publish,
   вместе с существующими проверками длины и стиля.
3. Генерация для бота сохраняет только прошедший линтер текст. Если попытки
   исчерпаны, прежний черновик и статус сохраняются. Бот показывает причину отказа
   и команду повторной генерации. CLI draft сохраняет прежнее поведение при отказе:
   переводит пост в killed с причиной. Невалидная доработка critique не заменяет файл
   и сохраняет текущий статус с флагом needs_review.
4. Одобрение в боте и оба пути публикации заново проверяют сохранённый файл:
   старая кнопка одобрения не позволяет отправить изменённый невалидный текст.
   Эта последняя проверка касается формата; замечания существующего линтера к стилю
   по-прежнему могут требовать ручного решения.
5. Подпись отправляется в Telegram как обычный текст, без Markdown/HTML-парсинга.

## Проверка и граф проекта

```sh
nix develop path:. --command python -m pytest -q
graphify update .
```

Локальный граф и интерактивная схема находятся в `graphify-out/graph.json` и
`graphify-out/graph.html`. Каталог исключён из Git как воспроизводимый результат.
